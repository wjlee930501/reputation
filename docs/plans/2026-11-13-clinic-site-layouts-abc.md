## 1. 바꾸지 않는 것 (SEO·AEO·GEO 계약)

레이아웃은 **표현 계층만** 바꾼다. `site/app/[slug]/page.tsx`의 데이터·구조화 데이터 계층은 그대로 두고, 세 안 모두 같은 입력을 받는다.

- **구조화 데이터:** MedicalClinic·Physician·Breadcrumb·FAQPage JSON-LD, canonical·OG, sitemap, robots, llms.txt는 레이아웃과 무관하다.
- **화면과 묶인 계약** — 세 안 모두 지켜야 한다. 기존 테스트가 고정한다.
  - 홈 FAQ 섹션은 FAQPage와 같은 항목이다(`schema.test.ts` 3건).
  - 질문 목록은 FAQ와 겹치지 않는다.
  - 의료진은 스키마의 의료진 전원을 보인다.
  - 병원 기본 정보는 스키마·llms.txt와 같은 값이다(NAP·HIRA·공식 채널).
  - 진료 항목은 하위 페이지로 링크한다.
  - 갤러리는 `/visit#gallery`로 링크한다.
  - h1은 하나이고 h1 > h2 > h3를 지킨다.
  - 없는 데이터는 섹션째 숨기고, 가짜 내용을 만들지 않는다.
- **페이지 내 앵커:** `#treatments #doctor #contents #facts #contact`는 세 안 모두 같은 id로 둔다. `CarePrinciples`가 `#contact`를 참조한다. A·C에는 '오시는 길' 섹션이 따로 없으므로 기본 정보 블록에 `id="contact"`를 단다.

## 2. 결정 (2026-11-13 확정)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 기존 운영 14곳 | 배포로는 바뀌지 않는다. 마케터가 병원마다 고를 때만 바뀐다 |
| 2 | 적용 범위 | 홈은 안별 구성, 하위 페이지는 헤더·푸터·서체·색만 |
| 3 | 신규 병원 | 계약 등록에서 필수 선택(권고안대로) |
| 4 | A안 첫 화면 사진 | HERO 승인 병원 사진 |
| 5 | 고르는 화면 | 정적 썸네일 3장 + 한 줄 설명(권고안대로) |
| 6 | 같은 지역 분포 | 보여 준다 |

각 항목의 근거는 아래와 같다.

1. **기존 운영 14곳:** 권고 — **배포만으로는 어느 사이트도 바뀌지 않는다.**
   - 값이 없으면(NULL) 지금의 As-is 렌더러를 그대로 쓰고, 마케터가 병원마다 명시적으로 안을 고를 때만 바뀐다.
   - 14곳이 모두 옮기면 As-is 렌더러를 걷어낸다.
2. **적용 범위:** 권고 — **홈은 안별로 다른 구성**, 하위 페이지(`/doctor` `/treatments` `/contents` `/visit`)는 **헤더·푸터·서체·색 토큰만 안을 따른다.**
   - 하위 페이지의 본문 구조까지 안별로 나누는 일은 후속으로 둔다.
3. **신규 병원 기본값:** 권고 — 계약 등록에서 **필수 선택**(미리 골라 두지 않음)으로 한다.
   - 사이트는 프로필 완료 뒤 자동 공개되므로, 레이아웃을 프로필 완료 조건에 넣지 않는다.
   - 값이 비는 예외 경로가 생기면 B로 보인다.
4. **A안 첫 화면 사진:** 권고 — 시안의 원장 사진 자리를 **HERO 승인 병원 사진**(`hero_image_url`)으로 바꾼다.
   - 원장 사진은 `DOCTOR_IDENTITY` 용도만 승인돼 있다.
   - 원장 사진을 첫 화면에 쓰려면 그 용도를 따로 승인받는다.
5. **고르는 화면:** 권고 — 1차는 **정적 썸네일 3장과 한 줄 설명**으로 한다. '이 병원 데이터로 미리보기'는 후속이다.
6. (선택) **같은 지역 병원이 쓰는 안 표시:** 권고 — 고르는 화면에 "같은 지역(예: 대구) 공개 병원: A n곳 · B n곳 · C n곳"을 보인다.
   - 원래 요청(대구 중복 우려)에 바로 답한다.
   - 지역은 `region` 첫 토큰의 시·도로 묶는다.

## 3. 반영 설계

### 3-1. 데이터 (마이그레이션 0095, 추가형)

- **컬럼:** `hospitals.site_layout VARCHAR(1) NULL`, `CHECK (site_layout IN ('A','B','C'))`
  - NULL = As-is(전환 전)이다. 기존 행은 그대로 둔다.
- **같은 길을 탄 선례:** `site_access_mode`(마이그레이션 0051). 선례가 지나는 곳은 다음과 같다.
  - backend: `models/hospital.py`, `schemas/hospital.py`, `api/admin/hospitals.py`의 `HospitalProfileUpdate`·변경 허용 목록·`CLEARABLE_FIELDS`·`PUBLIC_PROFILE_FIELDS`·관리 직렬화, `api/public/site.py` 직렬화
  - site: `site/lib/hospital-payload.ts`(타입·검증·정규화)
  - admin: `admin/types/index.ts`, `admin/lib/profile-patch.ts`, `admin/lib/clinic-visual-form-sync.ts`, `admin/app/hospitals/[id]/info/ClinicVisualForm.tsx`
  - 테스트: `test_hospital_visual_identity.py`, `test_public_site.py`, `info-page-contract.test.ts`

### 3-2. Backend

- **프로필 수정:** `HospitalProfileUpdate.site_layout: Literal["A","B","C"] | None`
  - 빈 문자열은 None으로 받는다(선례의 `blank_selection_clears_field`).
  - `PUBLIC_PROFILE_FIELDS`에 넣는다. 공개 병원에서 바뀌면 홈·하위 페이지를 즉시 다시 그린다(`hospital_site_paths`).
  - 즉시 갱신이 실패해도 저장은 그대로이고, 최대 30분(ISR 1800초) 뒤에 반영된다.
- **감사·서명:** 프로필 PATCH의 기존 감사(`changed_fields`)와 사람 계정 서명(BFF actor 단언)이 그대로 적용된다. 바꾼 사람·시각이 남는다.
- **계약 등록:**
  - `ContractRegistration`(`schemas/handoff.py`)에 `site_layout: Literal["A","B","C"]`를 필수로 넣는다(결정 3).
  - 병원 생성과 같은 트랜잭션에 저장하고, 등록 감사 detail에 남긴다.
  - 옛 Admin이 이 필드 없이 보내는 동안은 배포 순서로 막는다(§4).
- **자동 입력:** 자동 입력(`profile_autofill_apply`)은 이 필드를 쓰지 않는다. 지금도 사이트 표현 필드는 건드리지 않음을 확인했다.
- **readiness:** 시각 요소 준비 상태(`clinic_visual_readiness`)에 넣지 않는다. 기본값이 있으므로 막을 이유가 없다.

### 3-3. Admin

- **계약 등록 `/hospitals/new`:**
  - '사이트 레이아웃' 라디오 카드 3장(썸네일 + 한 줄 설명)을 둔다. 필수다.
  - 결정 6을 채택하면 같은 지역 분포를 함께 보인다.
- **병원 정보 탭 '사이트 표현' 폼(`ClinicVisualForm`):**
  - 같은 카드 3장으로 바꿀 수 있게 한다.
  - 공개 중인 병원이면 저장 전에 확인을 받는다. 확인 문구는 "공개 사이트의 홈 구성이 바뀝니다. 내용은 그대로입니다."이다.
  - 문구는 `ADMIN_COPY`에만 두고 copy-guard를 통과시킨다.
- **썸네일:** 캔버스 보드에서 첫 화면을 잘라 `admin/public/`에 정적 이미지로 둔다.

### 3-4. Site

- **page.tsx:**
  - 지금의 데이터·스키마 블록(141~253행)을 그대로 두고, 화면 입력을 하나의 모델로 묶는다(FAQ 항목, 질문 목록, 의료진, 사실 패널 값, 밀도, 사진 모드…).
  - 그 모델로 `<HomeLayoutA|B|C>`를 렌더링한다. NULL이면 지금 구성(As-is)이다.
  - FAQ·질문 선택처럼 계약에 걸린 선택은 **페이지에서 한 번만** 계산하고, 레이아웃은 받아서 그리기만 한다. 레이아웃마다 다시 고르지 않는다.
- **컴포넌트:**
  - 계약을 지는 블록(FAQ·사실 패널·질문 목록·의료진 목록·갤러리 링크)은 **의미 구조가 같은 컴포넌트**에 레이아웃별 마크업 변형만 둔다.
  - 장식 블록(첫 화면·빠른 안내 띠·진료표)은 레이아웃 전용이다.
- **CSS:**
  - 지금 병원 스타일은 `site/app/globals.css` 한 파일(9,601행)에 있다.
  - 레이아웃 스타일은 레이아웃별 파일로 나누고, 루트 클래스 `clinic-shell--layout-{a|b|c}` 아래로 범위를 한정한다.
  - `clinic-visual-system.test.ts`는 지금 `globals.css`만 읽는다. **레이아웃 CSS 파일도 같은 검사**(토큰 간격, 버튼 반경·굵기, 그림자 금지, 제목 크기 순서)를 받게 넓힌다.
- **색:**
  - 시안은 장보고의 짙은 청록·청록을 직접 썼다. 구현은 `buildClinicThemeStyle`의 `--clinic-*` 토큰(brand, accent, accent-strong, brand-action…)만 쓴다.
  - 금색 계열 병원(장앤김·행복드림)에서 대비를 따로 확인한다.
- **서체:**
  - A·B는 명조(나눔명조 400/700/800)를 쓴다. CSP가 `font-src 'self'`이므로 Pretendard처럼 `scripts/build_font_subsets.py`로 서브셋을 만들어 직접 호스팅한다.
  - C는 Pretendard만 쓴다.
- **줄바꿈:** 세 안 모두 `word-break: keep-all`을 쓴다. As-is의 단어 중간 줄바꿈이 가장 큰 어색함이었다.
- **하위 페이지:** `ClinicHeader`·`ClinicFooter`·`clinic-shell` 클래스에 레이아웃 변형을 넘긴다(결정 2).

## 4. 배포 순서와 롤백

1. **마이그레이션 0095**(추가형): 기존 행은 NULL이다.
2. **Backend:** 필드 수용. 계약 등록의 필수 검증은 Admin 배포 뒤에 켜거나, Admin과 같은 날 배치 시간대 밖에 배포한다.
3. **Site:** 필드가 없거나 모르는 값이면 As-is로 그린다. 그래서 Backend보다 먼저 나가도 안전하다.
4. **Admin:** 선택 화면을 연다.

- 배포만으로 운영 14곳의 화면은 바뀌지 않는다(결정 1).
- 롤백은 Site 트래픽을 되돌리면 모든 병원이 As-is로 돌아온다. 컬럼은 남겨도 무해하다.
- 배포는 `scripts/deploy.sh` 규칙(배치 시간대·env 정본)을 따른다.

## 5. 아직 확인하지 않은 것

- 세 시안은 **장보고 한 곳의 데이터**로, 캔버스용 자체 렌더러에서만 그려 봤다(1440px·390px). 실제 Next 런타임, 다른 병원 데이터, 금색 브랜드, 원장 2명, 글이 적은 병원에서는 보지 않았다.
- 페이지 길이: 데스크톱 기준 A 약 6,600px, B 약 7,600px, C 약 6,200px. 줄일지는 구현 후 실제 병원들로 다시 본다.
- 하위 페이지는 시안이 없다(결정 2에 따라 헤더·푸터·토큰만).
