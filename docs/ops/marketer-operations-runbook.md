# 마케터 운영 안내

문서 버전: **3.2** · 갱신일: **2026-09-07 (Asia/Seoul)**
소스 기준선: **`39dc1f8a98abe9193a8e2202395d2272c370fe8e`**
구현 상태: **기준선 위 작업 로컬 검증 완료. 운영 전환·배포 전**

정상 콘텐츠 생성·발행·측정은 시스템이 진행한다. 운영자는 계약 인수, 공식 정보와 공개 주소 확인, 자동 복구가 해결하지 못한 예외, 고객에게 보고서 전달을 맡는다. Slack이 조용하다는 이유로 작업을 다시 실행하지 않는다. 구조와 한계는 [시스템 구조](../architecture/system-map.md), 알림 기준은 [알림 정책](slack-notification-policy.md)을 본다.

## 1. 계약 인수와 프로파일

`/leads`에서 고객·담당자·계약 정보를 확인하고 온보딩으로 연결한다. 동일 병원 후보가 애매한 경우 임의로 중복 병원을 만들지 않고 기존 연결을 확인한다. 영업·운영 담당자와 인수 기록을 승인한 뒤 병원 프로파일을 완료한다.

프로파일 완료는 실제 필수 항목과 승인된 인수를 서버가 확인한다. 처음 완료될 때 V0 생성이 등록되며, 저장할 때마다 V0를 새로 측정하는 것은 아니다. `/hospitals/{id}/onboarding`의 현재 사유·다음 행동을 따른다.

## 2. 공개 화면과 콘텐츠 준비

병원 기본 화면과 콘텐츠 생성 준비는 별도다.

- 프로파일·V0·사이트 준비가 끝나면 기본 플랫폼 주소는 자동 활성화될 수 있다. 이를 위해 콘텐츠 일정을 먼저 설정할 필요는 없다.
- 자기 도메인은 도메인 패널의 관리 방식·DNS 안내·검증 결과를 따른다. 기본 주소 운영과 자기 도메인 연결을 구분한다.
- 공식 자료를 등록·실질 변경하면 일반 텍스트 자료는 전체 대상과 진행 위치를 저장한 처리 실행에 연결된다. 화면 저장 성공은 실행 접수이며, 전체 처리 종결과는 구분한다.
- 실행은 남은 자료를 자동으로 이어서 처리하고 broker/worker 유실이나 멈춘 lease는 재조정이 회수한다. 재조정은 15분마다 병원 200곳씩 순환하므로 450곳이면 한 번 전체 확인에 약 45분이 걸릴 수 있다. 15분을 개별 완료 기한으로 보거나 같은 값으로 다시 저장하지 않는다. 사진·제외 자료·추출 원문이 없는 URL은 자동 텍스트 처리 대상과 구분한다.
- 자동 검토 중이나 이미지 자동 복구 중인 건은 반복해서 수동 실행하지 않는다. 자동 검토가 해결하지 못한 근거 충돌이나 운영자가 맡은 초안은 해당 사유를 확인한다.

추가 자료 처리 중에는 신규 생성이 기다릴 수 있다. 기존 승인 근거가 온전하면 이전 공개 콘텐츠는 유지할 수 있으므로 자료 대기와 전체 사이트 중단을 같은 것으로 보지 않는다.

## 3. 운영센터에서 예외 확인

`/operations`에서 사람이 처리해야 하는 항목을 우선 확인한다. 실행 중이거나 처리 기한 안에서 재시도 중인 작업은 사람의 할 일로 표시하지 않는다. 최종 차단, 처리 기한을 넘긴 예외, 공식 정보·공개 주소·고객 전달처럼 사람이 결정해야 하는 항목만 처리한다. 같은 작업을 연속 재시도하면 공급자 호출이나 상태 경합을 늘릴 수 있다.

| 상황 | 확인할 사실 | 처리 |
|---|---|---|
| 콘텐츠 차단 | 자동 복구 중인지, 마감 이후에도 같은 원인인지 | 최신 자료·본문·이미지 차단을 읽고 서버가 허용한 조치 사용 |
| 일반 작업 실패 | 업무 상태와 연결된 작업 실행/문제 기록, 처리 기한 | 화면이 허용한 재시도에 사유를 기록; 행동이 없으면 문의 정보 전달 |
| 공개 정보 갱신 실패 | DB 저장 성공과 공개 캐시 반영 여부 | 재검증 복구 상태 확인; 원본 저장을 반복하지 않음 |
| 도메인 문제 | 현재 공개 주소·DNS·헬스 검사 | 도메인 패널 안내에 따라 수정 후 재확인 |
| 무료 진단 실패 | 측정/PDF/이메일 중 실패한 단계 | 해당 단계만 복구; 이메일 결과 불확실 시 중복 가능성 확인 |
| 알림 전송 실패 | 업무 결과와 outbox 전송 상태 | 필요한 알림만 복구; 업무 자체를 재실행하지 않음 |

안전한 행동이 없으면 `개발팀 문의용 정보 복사` 등 화면에서 제공하는 문의 정보를 사용한다. 원문 오류·비밀 값·신청자 개인정보를 운영 채널에 붙여 넣지 않는다. 개발 대상 인시던트는 개발 채널 또는 Admin에서 처리한다.

## 4. 콘텐츠 후행 확인

`/hospitals/{id}/content`에서 첫 순번 콘텐츠나 공개 후 본문 변경 등 검수 대상으로 표시된 항목을 확인한다. **매 글을 승인해야 발행되는 구조가 아니다.** 정상 자동·수동 발행의 Slack 성공 알림은 현재 만들지 않는다. 옛 안내의 “모든 발행 Slack 다시 보내기”를 일상 업무로 적용하지 않는다.

자동 검수는 전체 공개 후보와 항목별 검수 범위를 기록하고, 해결되지 않은 중대 문제와 불확실한 판정을 발행 전에 막는다. 생성 당시 운영 기준과 최근 재검사 운영 기준은 별도 이력이다. 이미지는 생성·정책 검수·업로드가 분리되고, 내용·글 주제·정책 버전에 묶인 인증이 현재 글과 맞아야 한다. 운영자가 제목·본문·이미지 의미를 바꾸면 기존 판정이 그대로 유지된다고 가정하지 않는다.

현재 공개 글 전환 preflight는 AI 검수 미해결 22건(REVISE 19, UNAVAILABLE 3), AI 검수 레거시 기준 허용 93건(ABSENT 92, PASS 1), 질문 끝 물음표만 고칠 FAQ 3건을 확인했다. 이 숫자는 운영자가 수동 편집할 목록이 아니다. 배포 Job이 exact allowlist와 CAS로 FAQ 3건을 고치고, 변경 후보를 포함한 22건을 독립 재검수한다. AI 검수 레거시 93건은 과거 메타데이터가 없다는 이유만으로 재검수하지 않으며, 배포 절차가 전체 전환 뒤 exact baseline ID 집합에서 새 엄격 공개 gate의 결과를 read-only로 확인한다.

기존 공개 이미지의 결합 인증 보강은 배포 절차의 일회성 Job/CLI가 공개 글 115건 모두를 실제 바이트 기준으로 처리한다. 운영자는 인증값을 직접 채우거나 임시 우회를 요청하지 않는다. 실제 바이트 검수에서 안전하지 않다고 확정된 이미지는 시스템이 먼저 숨기고 교체하며, Job이 종결하지 못한 경우만 운영센터의 행동 가능 예외를 따른다. 비공개 기존 글은 일반 생성·발행의 엄격한 이미지 인증 절차를 따른다.

공개 페이지에서 제목·본문·이미지·근거를 확인한다. 문제가 있으면 해당 글의 수정·비공개·재생성 흐름을 사용한다. 편집 후 재검사 때문에 DB에는 PUBLISHED여도 공개 필터에서 숨겨질 수 있으므로 공개 URL과 서버 사유를 함께 확인한다.

지연 콘텐츠는 시스템이 미래 일정으로 보충할 수 있다. 월을 넘긴 보충은 원 계약 월을 유지하며 실제 공개일을 과거로 바꾸지 않는다. 지정 요일 외 날짜나 하루 여러 슬롯은 월간 계약 편수 보완에서 발생할 수 있다.

## 5. 월간 보고서와 원장 전달

매월 1~7일 00:15에 전월 리포트 생성·복구가 실행된다. 09:00 작업은 남은 공백을 요약하는 알림이며 그 작업 자체가 보고서를 다시 만들지는 않는다.

`/hospitals/{id}/reports`에서 다음을 확인한다.

1. 계약 월 실적·실제 발행·보충 발행의 구분
2. 측정의 COMPLETE/LIMITED/UNAVAILABLE, 누락과 전월 비교 가능성
3. 검증된 원장용 PDF와 전달 차단 사유
4. 현재 파일에 연결된 전달·정정·철회 이력

측정 COMPLETE만으로 전달 가능하지 않다. 서버가 닫힌 측정 근거, 필요한 커버리지와 실패 상태, 원장용 파일 검증, 현재 운영 기준 차단을 함께 확인한다. 비교 불가한 결과를 상승·하락으로 설명하지 않는다. 내부용 PDF 대신 **원장 전달용 판본**을 사용한다.

AE가 실제로 전달한 뒤 Admin에 전달 사실을 기록한다. `전달 기록을 남겼습니다`는 이력을 저장했다는 뜻이며 시스템이 원장에게 이메일을 보냈다는 뜻이 아니다. 전달 직전 파일 hash와 최신 상태를 다시 확인하므로 그 사이 상태가 바뀌면 새 사유를 읽는다. 정정·철회·재전달은 기존 기록을 덮어쓰지 않고 별도 이력으로 남긴다.

V0는 초기 진단용 단일 PDF지만 작업 구현에서는 월간 원장용 PDF와 같은 방식으로 경로·hash·크기·검증 상태를 가진 artifact를 만든다. 현재 artifact가 유효할 때만 다운로드와 전달 기록을 진행한다. 전달 기록이 막히면 반복 실행하지 말고 해당 리포트 ID와 화면 사유를 개발팀에 전달한다.
