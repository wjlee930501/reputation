# Re:putation Slack 알림 정책

문서 버전: **2.6** · 갱신일: **2026-09-12 (Asia/Seoul)**
소스 기준선: **`55fa24e10e7107edd97851fd3261c3cd622c2625`** 위 변경
구현 상태: **기준선 위 V0 공개 게이트 분리·자동 이어가기 구현 및 검증 중. 운영 배포 전**
범위: 현재 알림 정책과 코드 경계. 실제 수신 채널은 webhook 설정으로 결정되며 이번 문서 갱신에서 Slack 메시지를 보내지 않았다.

운영 채널은 `#mkt-reputation`이며, `SLACK_WEBHOOK_URL`이 연결된 채널이 실제 수신처다.
Incoming Webhook은 코드에서 채널을 바꾸지 못하므로 배포 전 웹훅이 이 채널에 연결됐는지
Slack 앱 설정에서 확인한다.

## 원칙

Slack은 로그 저장소가 아니라 사람이 행동을 결정하는 화면이다. 알림은 아래 셋 중 하나로만
분류한다.

1. **즉시 대응**: 새 영업 기회 또는 자동 복구가 끝난 최종 실패
2. **운영 요약**: 같은 실행에서 여러 병원·콘텐츠에 발생한 결과
3. **로그 전용**: 정상이며 사람이 할 일이 없는 이벤트

병원 수나 콘텐츠 수만큼 메시지를 반복하지 않는다. 배치 작업은 병원별 한 줄을 포함한 메시지
한 건으로 끝내고, 상세 개인정보·원문·긴 오류는 Admin 또는 구조화 로그에서 본다.

연락처와 이메일은 항상 마스킹한다. Slack에 표시되지 않은 신청 정보는 Admin 리드 화면에서만
확인한다.

### 온보딩·월간 마일스톤 계약

- 같은 15분 창의 이벤트는 병원 수와 관계없이 한 요약으로 보낸다. 병원별 성공 메시지는 보내지
  않으며, `ACTIVE`는 같은 병원의 인계 수락·활성화 준비를, 활성화 준비는 인계 수락을 대체한다.
- 상태 전환과 구성 이벤트 ID로 중복 키를 결정한다. 같은 창을 다시 투영해도 outbox 행이나 Slack
  메시지가 늘어나지 않는다.
- 마지막 관측 상태는 `OperationRun` projection cursor에 함께 저장한다. 배치 실행 구간을 놓쳐도
  다음 실행이 이전 스냅샷과 현재 DB truth를 비교해 늦은 차단·복구·고객 전달 준비 전이를 포착한다.
- 월간 집계 `COMPLETE`는 내부 커버리지 완료일 뿐 고객 전달 준비 완료가 아니다. 닫힌 manifest,
  계획된 셀 전부 성공, 실패 0건, 검증 상태 `VALID`인 원장용 산출물, 현재 운영 기준 차단 0건을
  서버 게이트가 모두 확인한 경우에만 `CUSTOMER_READY`를 표시한다. 그 전에는 산출물 검증 대기로
  표시한다.
- 전달 정정·철회·재전달은 현재 준비 상태를 추정하지 않고 append-only 전달 이벤트 ID로 투영한다.
- 메시지에는 안정적인 이벤트 ID, 고객 영향, 담당자와 처리 기한, 다음 행동과 Admin 링크를 포함한다.
  한 메시지에는 `/operations` 또는 해당 리포트 상세 링크 중 정확히 하나만 넣는다.
- 운영자 문구는 `무슨 문제인지 → 고객 영향 → 지금 할 일` 순서로 쓰고, 영문 `SLA` 대신
  `처리 기한` 또는 `인수 처리 기한`을 사용한다. 내부 enum·오류 코드는 Slack에 노출하지 않는다.
- GCS·파일시스템 경로, 원문 응답, 이메일·전화번호 등 개인정보는 Slack에 넣지 않는다.

Slack은 DB 상태의 읽기 전용 투영이다. 도메인 트랜잭션은 Slack 성공 여부를 기다리지 않으며,
전송 실패로 인계·활성화·리포트 상태를 되돌리지 않는다. 실패는 outbox와 알림 incident에 남아
Admin에서 확인·재시도할 수 있어야 한다.

## 자동 복구는 사람의 확인을 요구하지 않는다

자동 재시도가 스스로 복구한 인시던트는 시스템이 `ACKNOWLEDGED`로 종료한다
(`acknowledged_by_id`가 비어 있으면 시스템 종료, 채워져 있으면 사람이 확인한 것이다).

**정책 목표는 OPEN과 RECOVERED를 쌍으로 관리하는 것이다.** 실제 공통 복구 구현은
`notify=True`이며 OPEN 공지가 outbox에 등록된 이력이 있을 때 복구 공지를 등록한다.
`notify=False`인 복구 경로도 있으므로 모든 복구가 반드시 Slack 메시지를 만든다고 해석하지 않는다. 억제 판단의 유일한 근거는 시간이 아니라 **그 인시던트의
`INCIDENT_OPEN` 공지가 outbox에 들어갔는지**다(`services/dependency_incident_helpers.py`의
`open_notice_exists`). 파이프라인이 이미 자기 인시던트를 낸 경우나 `notify=False`로 연
경우처럼 OPEN이 나간 적 없는 건은 복구도 Slack 없이 DB 인시던트·감사 로그로만 남는다.
"30분 안에 조용히 복구된 건은 아무 메시지도 보내지 않는다"는 기준은 실제로는 RECOVERED만
지워서 아무도 닫지 않는 "운영 확인 필요"를 채널에 남겼기 때문에 폐기했다. 복구 메시지는
정보 전달용이라 "‘확인 완료’ 처리하세요" 같은 행동 요구를 넣지 않는다.

07:45·08:00 발행 차단은 콘텐츠 건별이 아니라 배치당 한 건의
요약으로 보낸다. `PROVIDER_TIMEOUT`, `PROVIDER_UNAVAILABLE`, `GENERATION_FAILED`는 당일
발행 슬롯의 07:45 전까지 개별 알림 없이 자동 복구하고, 남아 있는 `GENERATION_FAILED`는
07:45 아침 요약에, 공급자 일시 오류는 08:00 요약에 넣는다. 비용 차단은 비용 가드의 단일 즉시
알림이 소유하며, 이미 발행된 글의 이미지 재인증 조치 필요 코드만 생성 경로에서 즉시 알린다.
가격·GEO·SEO·FAQ·근거·금지 표현·
독립 검수처럼 입력/원고 검수에 속한 코드는 개별 즉시 알림과 아침 요약에서 제외하고 월요일
주간 요약 한 건으로만 보낸다. `GENERATION_LEASE_ACTIVE`, `STALE_GENERATION_CLAIM`, 이미지 생성·검증
계열은 07:45 복구를 넘겨 08:00까지 남은 경우에만 아침 요약에 넣는다. 새 자료가 들어와
Essence 갱신을 기다리는 상태도 그 자체로 알리지 않으며, 당일 발행 마감까지 해결되지 않아
실제 공개 지연을 만드는 경우에만 차단 요약에 포함한다. 운영센터 큐에서도 08:00 이전의
당일 발행 예정 슬롯과 `RETRYING` 인시던트는 사람의 일이 아니므로
`requires_operator_action=false`로 접어서 표시한다.

AE가 고칠 수 없는 순수 인프라 인시던트(`BACKGROUND_TASK_FAILED`, `BROKER_UNAVAILABLE`,
`UNSAFE_STORED_DISPATCH`, `NOTIFICATION_DELIVERY_FAILED/UNKNOWN`,
`CACHE_REVALIDATION_FAILED`, `MONTHLY_DOCTOR_PDF_BLOCKED`)는 인시던트 타입 레지스트리에서
`audience = "developer"`로 표시하고 `SLACK_WEBHOOK_URL_DEV`가 설정된 경우 개발 채널로
보낸다. 레지스트리에 없는 타입의 기본값은 `operator`다. `SLACK_WEBHOOK_URL_DEV`가 비어
있어도 개발 채널 알림을 운영 채널로 폴백하지 않는다. 해당 outbox 행은
`DEV_WEBHOOK_MISSING` 코드와 함께 `HOLD`로 남고 worker가 오류를 기록하므로, 설정 후 Admin에서
수동 재시도할 수 있다. **배포 전 `SLACK_WEBHOOK_URL_DEV`가 실제 개발팀 채널 webhook으로
설정되었는지 확인한다.**

## 중복 억제와 재알림

- 생성·발행 차단 요약은 **병원 ID·콘텐츠 ID·예정일·차단 코드·안전한 사유·생성 시도
  fingerprint 집합**으로 중복 키를 만든다. 이 집합이 같으면 날짜나 07:45/08:00 배치가
  달라도 다시 알리지 않고, 일정·원인·입력 상태가 실제로 바뀐 경우에만 새로 알린다.
- 생성 검수 거절은 같은 생성 입력 fingerprint에서 공급자 호출과 인시던트 재개를 반복하지
  않는다. 주간 요약은 KST 주 시작일을 중복 키로 사용해 재디스패치돼도 그 주에 한 건만 만들고,
  병원별 안전한 원인과 건수만 보여준다. 원문 후보·공급자 오류 본문은 Slack에 넣지 않는다.
- 자료 처리 또는 Essence 자동 검토 대기만으로 별도 알림 중복 키를 만들지 않는다.
- Slack 전송 실패는 outbox의 같은 행을 제한된 횟수로 재시도한다. 소진된 실패는 Admin에서
  명시적으로 재시도하며, 도메인 상태를 되돌리거나 같은 업무 이벤트를 새로 만들지 않는다.
- 신규 진단 접수는 `PENDING → SENDING → SENT/FAILED`로 원자적으로 claim해 중복 작업이
  동시에 같은 접수를 보내지 못하게 한다. API가 Redis에 넣지 못해도 1분 폴러가 PENDING을
  다시 회수한다.

## 로그에만 남기는 이벤트

- 자동 파기 대상이 0건인 정상 실행
- 생성·측정 대상이 0건인 정상 실행
- 이미 처리된 멱등 작업
- 자동 재시도 중이며 아직 최종 실패가 아닌 외부 API 오류
- 답변 저장 뒤 판정만 재개되는 측정, 비용 차단 재개 시각 대기와 예산 초기화 뒤 자동 재개
- 네이버 자료의 정상 수집·처리, 최신 전체 snapshot 기반 Essence 자동 합성·검토·승인
- IndexNow 제출 의도 기록·재시도 성공과 공급자 사용량 임시 큐의 복구 성공
- 콘텐츠 자동 발행 및 수동 복구 발행 성공. 현재 두 발행 경로 모두 `CONTENT_PUBLISHED`
  Slack outbox를 만들지 않으며, 공개 상태·감사 로그·재검증 결과가 실행 증적이다.
- `INCIDENT_OPEN` 공지가 나간 적 없는 인시던트의 복구 사실 (위 “자동 복구는 사람의 확인을
  요구하지 않는다” 참고 — 복구 알림이 허용된 경로에서 OPEN 등록 이력이 있으면 복구 알림을 등록한다)

0건 파기라도 작업 로그와 모니터링 지표에는 남는다. Slack에서 없앤 것이지 실행 기록을
없앤 것이 아니다.

## 배포 전 확인

1. `SLACK_WEBHOOK_URL`이 `https://hooks.slack.com`이며 `#mkt-reputation`에 연결돼 있는지 확인
2. 테스트 접수 한 건으로 마스킹·Admin 링크·접수 순번 확인
3. `GENERATION_REJECTED`와 가격·GEO·SEO·금지 표현 계열은 즉시/07:45/08:00 Slack이 없고
   월요일 주간 요약 최대 한 건에 병원·원인이 포함되는지 확인. `PROVIDER_TIMEOUT`,
   `PROVIDER_UNAVAILABLE`, `GENERATION_FAILED`는 07:45 전까지 조용하고 각 아침 요약 시점에만
   포함되며, `COST_BLOCKED`와 발행된 이미지 재인증 실패만 소유 경로에서 즉시 한 건인지 확인
4. Slack 실패 시 DB의 `notification_outbox.state`가 `FAILED`로 남고 신청 응답 자체는 성공하는지 확인
5. 온보딩·월간 요약에 안정적인 ID, 담당자·처리 기한·고객 영향, fallback text와 Admin 링크가 정확히 한
   개인지 확인
6. 월간 `COMPLETE`만으로 `CUSTOMER_READY`가 발행되지 않고, 원장용 산출물 검증과 현재 차단
   게이트를 모두 통과한 경우에만 발행되는지 확인

자동 테스트와 QA는 MockTransport로 payload·실패·재시도만 검증한다. 실제 Slack 채널에는 테스트
메시지를 게시하지 않고, 필요 시 읽기 전용 검색으로 QA 게시물 0건을 확인한다.
