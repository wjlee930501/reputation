# Slack 메시지 운영 체계

정책 버전: 4.1 · 2026-10-10. 코드 기준: PR #226·#227·#228(운영 채널 하나·채널 상태·사람의 일 술어).
상태: main 통합 정책. 운영 배포 여부는 별도 릴리스 기록으로 판단하며 이 문서는 배포 완료를 뜻하지 않는다.

## 알림 종류 라벨과 행동 안내

모든 발송 메시지는 `notification_labels.py`의 종류 라벨로 시작한다. fallback text와
Block Kit header(헤더 없는 직접 알림은 첫 section)가 같은 분류를 표시한다.

| 종류 라벨 | 분류 |
|---|---|
| `[Lead : 도입 문의]` | 도입 문의·무료 진단 신청 |
| `[Error : 오류 발생]` | 실패·차단·조치 요청. 전달 준비 완료·사이트 준비/공개 완료·자동 복구가 도는 월간 공백은 여기 아님 |
| `[Report : 운영 현황 보고]` | 관측된 복구·일일 및 주간 운영 보고·전달 준비 완료 마일스톤(`MILESTONE_SUMMARY_REPORT`)·사이트 준비/공개 완료·자동 복구가 진행 중인 월간 공백(`MONTHLY_REPORT_GAP_AUTO`) |

종류 라벨 바로 뒤에 붙는 표시 두 개는 라벨이 아니라 전송 경로의 사실이다 — `[개발 확인]`은 개발 담당
몫의 알림이 운영 채널로 왔다는 뜻, `[채널 대체 전송]`은 원래 채널의 웹훅이 죽어 다른 채널로 왔다는 뜻이다.
저장된 payload에는 붙이지 않고 전송 사본에만 붙인다.

세 문자열과 `EVENT_LABELS`의 이벤트별 대응은 PR #134 그대로 유지한다. 라벨 뒤의
`[긴급]`, `[조치 필요]`, `[업무 알림]`, `[복구]`, `[일일 요약]`은 메시지의 구체적
상태다. 종류 라벨을 발송 조건이나 채널 라우팅으로 쓰지 않으며 중복으로 붙이지 않는다.

PR #134의 라벨 계약과 9월 17일의 행동 중심 문구·정상 알림 억제를 함께 적용한다.
과거 메시지 문장을 그대로 보존한다는 이전 정책은 이 통합 문구 규칙으로 대체한다.
정상 개인정보 파기와 성공한 대체 이미지 발행에는 라벨을 보여 주기 위해 알림을
되살리지 않는다. 담당 행동·검증된 Admin 링크·안전한 참조 코드는 유지한다.

## 원칙

Slack은 작업 로그가 아니라 업무 전달 수단이다. 메시지를 읽은 사람이 지금 할 일을
판단할 수 있어야 한다. 자동 복구 중인 일을 사람에게 다시 시키지 않는다.
정상 생성·검수·발행·자동 자료 정리는 개별 알림 없이 원래 업무 기록에 남긴다.
성공한 대체 이미지 발행은 오류가 아니다. 집계할 때에도 차단된 글과 분리한다.

| 구분 | 수신자가 할 일 | 발송 기준 |
|---|---|---|
| `[긴급]` / `[조치 필요]` | 해당 화면의 구체적인 항목 처리 | 중요한 장애·실제 사람의 판단이 필요한 예외. 기존 incident episode와 수신 채널을 유지 |
| `[업무 알림]` / `[전달 준비]` | 자료 보완·고객 전달 등 남은 업무 처리 | 새로 바뀐 상태만. 월간 보고서는 병원·대상 월마다 최신 버전 하나(상태 키 `monthly:{hospital_id}:{YYYY-MM}`). 새 버전을 알리는 경우는 셋뿐 — 처음 준비 완료, 차단 뒤 다시 준비 완료, 전달 뒤 숫자가 바뀐 재빌드. 숫자가 같은 새 버전(TEMPLATE_REFRESH 포함)은 알리지 않는다. 정기 projector는 기존 15분 창에서 묶음 |
| `[복구]` | 별도 조치 없음 | 앞서 알린 문제의 관측된 복구. 종료된 고객 영향과 담당자 지정 요구를 반복하지 않음 |
| `[일일 요약]` / `[주간 요약]` | 미해결 담당 항목만 확인 | 기존 18시 일일·월요일 주간 요약 유지. 불필요한 새 주기 없음 |

새 문의와 무료 진단 접수는 상담 기회를 놓치지 않도록 개별 알림을 유지한다.
병원의 공개 운영 시작은 기존 standalone 생산자에서 병원당 한 번 알리며,
정기 마일스톤 projector가 같은 시작을 다시 알리지 않는다.
심각한 신규 장애·서로 다른 고객 신청을 하루 메시지 상한 때문에 버리지 않는다.

## 문장과 행동

제목에 종류·병원·상태를 넣고 첫 문장에 사실을 쓴다. 다음 문장은 담당자가 해야 하는
행동과 화면을 말한다. 버튼은 그 행동을 여는 하나의 링크로 제한한다.
`무슨 문제인지 / 고객 영향 / 지금 할 일`을 정상 접수와 복구까지 기계적으로 반복하지 않는다.

LLM 검수 원문·JSON 필드명·예외 본문은 Slack에 옮기지 않는다. 콘텐츠 메시지는
`본문·근거 확인`, `운영 기준 승인`, `이미지 준비`, `비용 한도`처럼 행동이 다른 이유를 구분한다.
자세한 지적은 인증된 Admin 화면에서 읽는다. 오류를 단순화하되 승인되지 않은 사실을 만들지 않는다.
확인된 담당자 이름만 표시한다. 이름을 모르면 운영/개발 담당 역할을 표시하며 미배정이라고 단정하거나 임의의 사람을 배정하지 않는다.
기한이 없으면 가짜 기한을 표시하지 않는다. 실제 기한·집계 창은 KST로 표시한다.
긴 개발팀 전달 안내는 제거하고 incident 참조 코드 한 개를 남긴다. 보안상 원본 UUID와 고객 원문은 싣지 않는다.

## 중복과 자동 진행

- 이미지 대체 발행만 있는 배치는 알리지 않는다. 다른 글의 차단 알림에 성공한 대체 발행을 섞지 않는다.
  새 대체 이미지가 생겨도 기존 차단 집합의 중복 키를 바꾸지 않는다. 재사용 편수는 주간 실적에 포함한다.
- 보고서의 과거 버전은 현재 업무 목록에서 제외한다. 대상 월은 반드시 표시한다.
  이전 버전에 대한 전달 수정·무효·재전달 이력은 별도 사실이므로 숨기지 않는다.
- 자동 PDF 검증 대기는 cursor에 기록하되 알리지 않는다. 고객용 파일이 실제 준비되면 전달 업무를 알린다.
  마감된 보고서의 최종 미완료와 현재 병원 근거 자료의 차단은 여전히 사람에게 알린다.
- 월간 차단이 이어지는 동안에는 관측 창마다 다시 알리지 않는다. 사람이 할 일을 가르는 값
  (필수 측정 집계 마감 여부, 현재 근거 자료 차단 여부)이 같으면 표본 수·재생성된 PDF 행·
  게이트 코드가 움직여도 같은 차단이다. 첫 차단과 다른 상태로의 전이는 그대로 알린다.
  이미 전달한 지난 계약 월은 현재 상태 스캔에서 빼고, 전달되지 않은 달은 기간과 무관하게 남긴다. 다만 같은 병원의
  더 나중 달이 전달 준비 완료이거나 전달됐으면, 그보다 이른 미전달 달의 차단·PDF 검증 대기 변화는 알리지 않는다
  (2026-10-09 전달 판정 변경 뒤 9월이 준비된 병원 7곳에 '8월 차단'이 나간 사례). 그 이른 달이 전달 준비 완료가 되면
  늦게라도 전달하도록 한 번 알리며, 알리지 않는 동안에도 상태 기억은 이어 가 나중 달이 다시 막혀도 옛 달을 재알림하지 않는다.
- 한 병원에서 종류·상태 문구·할 일이 같은 항목은 요약에서 한 줄로 접고 대상 월 수를 함께 쓴다.
  접기는 표시에만 적용한다 — 중복 키와 건수는 접기 전 항목 전부를 그대로 센다.
- 인수 승인·운영 시작 등 별도 조치 없는 상태 변화는 정기 projector가 중복 알리지 않는다.
  연체된 인수가 해결된 회복 알림과 실제 공개 주소 설정 업무는 유지한다.
- 정상 개인정보 파기 작업은 기존 처리 기록과 로그에 남기고 개별 Slack을 보내지 않는다. 실패 알림은 유지한다.
- 이미지 때문에만 막힌 글에 시간별 발행기가 거는 자동 이미지 재생성(시스템 실행, 글당 KST 하루 1회·
  누적 3회)은 알리지 않는다. 그 실행이 실패해도 개별 Slack을 보내지 않는다 — 예산 안의 복구는
  스윕이 소유하고, 소진된 이미지 차단은 종전처럼 아침 요약이 알린다. Admin “이미지 다시 만들기”의
  실패 알림은 그대로다.
- 독립 검수 장애(`CONTENT_AI_REVIEW_UNAVAILABLE`)는 자동 재검수 중에는 알리지 않는다. 같은 원고의
  자동 재검수가 한도(`CONTENT_AI_REVIEW_UNAVAILABLE_MAX_RETRIES`, 기본 6회)에 닿으면 인시던트가
  OPEN(사람의 일)이 되고, 그 전이에서 `[Error : 오류 발생]` 인시던트 알림을 한 번 보낸다. 같은
  episode에서는 다시 알리지 않으며, 원고를 고치면 새 후보로 자동 재검수가 다시 시작된다. 고친 원고가
  같은 episode 안에서 다시 한도에 닿으면 인시던트는 다시 OPEN이 되지만 두 번째 알림은 보내지 않는다.
- 07:45·08:00 발행 보류 요약은 새로 막힌 (글, 사고 epoch)만 알린다. 같은 글이 같은 epoch로 다음 날도 막혀
  있으면 다시 쓰지 않으며, 알린 사실은 `GENERATION_BLOCKED_NOTICE` 실행 기록으로 남는다. 두 번째 실행은 요약을 만들지 않는다.
- 월간 보고서 공백은 둘로 가른다. 자동 복구가 아직 도는 공백(측정 이어가기·재생성 예산 안)은 `MONTHLY_REPORT_GAP_AUTO`로
  Report이고, 자동 복구가 끝나 사람이 정해야 하는 공백만 `[조치 필요]`다. 분류가 바뀔 때만 알리고, 보고서가 준비되면
  그 공백 알림은 종료된다. 코호트 밖 병원은 월간 측정 대상이 아니므로 공백으로 세지 않는다.
- 사후검수 지적(`POST_PUBLISH_REVIEW_FLAGGED`)처럼 계약상 운영자 큐에 올리지 않는 조용한 종류는 Slack에도
  보내지 않는다(`incident_types.QUIET_INCIDENT_TYPES`).

일일 요약은 `병원 / 이유 / 건수 / 운영 또는 개발 담당 / 구체적인 할 일`을 먼저 보여준다.
사람의 일 건수는 `operator_action.is_operator_todo` 하나로 센다 — 기한이 지난 사람의 일이면서 운영 담당 몫이고
조용한 종류가 아닌 사고다. 일일 요약·운영센터 큐·현황 카드·병원 목록이 같은 술어와 같은 원인 묶음
(`incident_cause_group.cause_group_key`)을 쓰므로 요약의 건수와 운영센터의 묶음 수가 같다. 개발 담당 몫은
"개발 확인 M건"으로 따로 세고, 둘 다 0이면 "점검 이상 없음"이라고 쓴다.
자동 복구 수와 사람이 처리할 이슈 수를 분리한다. 대표 그룹 여섯 개를 보여주고 나머지 개수를 명시한다.
월간 약정·배정·최초 발행을 구분하며 다른 계약 월의 이월분을 이번 달 실적으로 합치지 않는다.
과거 보고서 생성 건수나 이미 복구된 실패 이력을 현재 업무처럼 제시하지 않는다.
주간 요약도 지난주 발행 실적과 현재 미해결 업무의 대상 기간이 다를 수 있음을 표시한다.

## 채널과 안전 경계

Slack 채널은 운영 채널 하나다(2026-10-08 대표 결정). incident 유형별 운영/개발 **대상**(`IncidentAudience`)은
유지하고 다른 수신 대상의 incident를 한 메시지로 섞지 않지만, 개발 전용 webhook이 비어 있으면(또는 시크릿 버전이
비활성이면) 개발 대상 알림은 종류 라벨 바로 뒤 `[개발 확인]` 표시와 함께 운영 채널로 간다. HOLD로 남기지 않는다.
수신처를 임의로 만들지 않는다.

설정된 웹훅이 3xx·403·404·410을 돌려주거나 미설정·허용 밖 주소면 채널 단위 전송 사고 하나
(`notification/channel/<채널>/CONFIGURATION_ERROR`)가 열리고, 그 사고가 정본이다. 400(본문 거절)은 그 알림 하나의
실패이며 채널을 죽은 것으로 보지 않는다. 사고가 열린 동안 그 채널 알림은 다른 채널로 `[채널 대체 전송]` 표시와 함께
가며, 전송 사고 알림은 그 사고가 가리키는 채널로 보내지 않는다. 한 시간에 한 번 `{}` 탐침(살아 있음 = 400
`no_text`/`invalid_payload`/`missing_text`, 죽음 = 3xx/403/404/410, 5xx·시간 초과 = 모름)으로 자동 복구하고, 보낼 곳이
없어 보류한 알림(`SLACK_CHANNEL_UNAVAILABLE`)은 HTTP 요청을 한 번도 하지 않았으므로 복구 때 다시 보낸다.
배포(`deploy.sh`)·준비 점검(`slack_webhooks_not_dead`)·탐침은 같은 분류를 쓴다. Celery 밖 pipeline watchdog도 개발
경보가 전달되지 않으면 운영 웹훅으로 대체 전송한다.

Celery 밖 pipeline watchdog은 **조건 집합 에피소드당 한 번** 알린다(2026-10-10, 같은 경보가 매시간 다시 나가던 문제).
같은 조건이 이어지는 동안 다시 보내지 않고, 전달이 확인되지 않은(실패·응답 불명) 경보만 15분마다 다시 시도하며 — 마지막 방어선이라 불명도 다시 보낸다 —, 조건이 사라지면 복구를 한 번
보낸다. Beat·대기열 정지와 `publish_missing`은 4분 이상 간격의 연속 두 점검에서 보여야 경보하고, 연속 두 점검에서 사라져야
복구한다 — 배포 중 Beat 재시작(1~3분)은 알리지 않는다. 발행 조건은 그날(KST)에 속해 자정에 조용히 사라지며 거짓 복구를 만들지
않는다. 발행기가 돌았고 공개 직전 안전검사가 예정 글을 모두 보류한 경우(`publish_gate_residual`)는 감시가 알리지 않는다 —
그 보류는 07:45·08:00 보류 요약·사고·18:00 일일 요약이 소유한다. 운영 복구 문구는 실제 공개가 있었을 때만 "다시 공개되고
있습니다"라고 쓴다. Redis 장애 중 fail-open 경보는 20분에 한 번(정각·20분·40분 뒤 5분 안)만 보낸다.

공개 주소 점검은 같은 도메인이 **연속 두 번** 실패해야 병원 사고를 연다(한 번의 일시 503은 기록만 남긴다). 한 점검 회차에서
두 병원 이상이 공용 사이트의 HTTP 5xx를 받으면 병원별 사고 대신 개발 대상 사고 `PUBLIC_SITE_UNAVAILABLE` 하나로 묶고, 그것도
연속 두 회차에서 보여야 연다. 시간 초과·TLS·마커 불일치는 병원별 원인일 수 있어 종전처럼 병원 사고다. 복구는 연속 세 번 정상이다. 전송 실패는 outbox 행의 `incident_id`(그 알림이 말하는 사고)를
덮어쓰지 않으며, 전송 사고는 `source_id`로 행을 가리킨다.

공개 도입문의 접수 알림(`notify_lead_created`)만 도입문의 전용 채널 `#noti-도입문의-뉴비짓`
(`SLACK_WEBHOOK_URL_INQUIRY`)으로 보낸다. 이 채널에는 뉴비짓의 다른 제품 문의도 함께 들어오므로
제목과 fallback text에 `[Re:putation]` 출처 표시를 종류 라벨 바로 뒤에 붙인다. 웹훅이 비어 있으면
기존 운영 채널(`SLACK_WEBHOOK_URL`)로 보낸다 — 고객 신청 알림은 HOLD로 잃지 않는다.
무료 진단 접수·개인정보 파기 실패 등 다른 알림은 운영 채널에 남는다. 요약은 처리방침의 Slack
국외 이전 고지 범위(병원명·진료과·지역·마스킹된 연락처·유입 경로(사이트의 알려진 경로만, 광고 쿼리 제외)·접수 시각·자동 처리
결과)만 담고 핵심 키워드·문의 본문·담당자 성함은 싣지 않는다.

incident와 작업의 정본은 DB다. 알림 전송 성공이 작업 성공·고객 수신·발행 성공을 뜻하지 않는다.
OPEN/RECOVERED의 episode 중복 키, outbox lease/CAS, 전송 재시도 상한은 변경하지 않는다.
전송 결과가 불명확하면 HOLD로 남기며 자동 재전송하지 않는다. 웹훅 주소가 죽어 전달되지 않은 것이 확실한
행(3xx·403·404·410)은 불명확이 아니므로 다른 채널로 다시 보낸다. 개인정보·secret·저장소 경로 마스킹,
허용된 Admin 링크 한 개, Slack 블록/텍스트 길이 제한을 함께 검증한다.
제목은 150자, section은 3,000자, fields는 10개·각 2,000자, 전체 블록은 기존 50개 이하다.

월간 수치는 확정 답변을 100번 기준으로 환산했음을 밝힌다. 명시적인 비교 가능 근거가 없으면
전월 증감을 만들지 않는다. `의미 있는 상승`, `정상 변동 범위`라는 단정은 Slack에 넣지 않는다.
레포트 준비 알림은 실제 고객 전송 완료가 아니다. AE가 원장에게 전달하고 전달 기록을 남긴다.

## 구현·검증 위치

문구: `notification_copy`, `notification_messages`, `notification_milestone_messages`,
`onboarding_notifications`, `content_publish_notifications`, `fleet_heartbeat`, `notifier`.
발송 선택: `milestone_event_tasks.should_notify_milestone`, `latest_report_facts`,
`enqueue_generation_blocked_digest_sync`. 사람의 일 술어: `operator_action.is_operator_todo`, 원인 묶음:
`incident_cause_group`. 채널 상태와 대체 전송: `notification_channel_health`, `notification_delivery`.
`monthly_report_gap_notifications`는 최종 LIMITED 결과도 공유 전달 게이트로 판단한다.

검증에는 실제 업무 DB와 분리한 PostgreSQL/Redis, mock Slack 응답을 쓴다.
실제 Slack 채널에 시험 메시지를 보내거나 기존 채널 이력을 수정하지 않는다.
이미 저장된 과거 outbox payload와 기존 Slack 글은 이번 코드 변경만으로 바뀌지 않는다.
스레드 자동 묶기·기존 Slack 글 수정은 구현한 기능이 아니다. 메시지 발생 조건에서 중복을 줄인다.
새 코드가 운영에 배포된 뒤 생성되는 메시지에 적용하며, 배포 상태는 릴리스 기록으로 구분한다.
