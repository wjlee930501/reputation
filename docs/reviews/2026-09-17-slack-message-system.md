## 실제 알림과 코드에서 확인한 문제

운영 채널을 읽기 전용으로 확인했다. 정상 신청도 ‘무슨 문제인지’로 시작했고,
복구 알림에 종료된 장애 영향과 담당자 지정 요구가 남아 있었다. 긴 모델 검수 원문과
내부 필드명이 그대로 표시돼 행동을 알아보기 어려웠다. 정상 이미지 대체 발행이
발행 차단 제목으로 나가고, 이미지 정책 거절에도 크레딧 확인을 요청했다.

월간 알림은 과거 보고서 버전까지 현재 상태로 투영하고 있어 같은 병원이 한 묶음에서
차단·전달 준비로 반복 등장할 수 있었다. 공개 운영 시작도 standalone과 projector가
각각 알렸다. 날짜는 UTC 문자열이었고 보고 대상 월이 없는 ‘이번 달 결과’가 붙었다.

## 바꾼 체계

| 분류 | 읽는 사람의 판단 | 보존한 발송 경계 |
|---|---|---|
| 조치 필요 / 긴급 | 병원·원인·해야 할 일·실제 화면 확인 | 기존 중요 장애의 incident episode와 수신 채널 |
| 업무 알림 / 전달 준비 | 남은 인계·자료 보완·고객 전달 수행 | 실제 상태 전이만 기존 15분 창으로 묶음 |
| 복구 | 추가 조치 없음 | 관측된 복구만 알림. 기존 OPEN/RECOVERED 대응 규칙 유지 |
| 일일 / 주간 요약 | 현재 미해결 담당 항목만 확인 | 기존 하루·주간 주기 유지 |

문구는 결정적 코드가 고른다. 메시지 작성에 LLM을 새로 호출하지 않는다.
한 메시지는 하나의 검증된 Admin 버튼을 제공한다. 확인된 담당자만 이름으로 표시하고,
없으면 담당 역할을 표시한다. 없는 기한을 만들지 않으며 실제 기한과 집계 창은 KST다.

## 발송량을 줄이는 실제 변경

월간 상태는 병원·대상 월별 최신 보고서만 투영한다. 과거 버전을 지우지는 않으며,
그 버전의 전달 수정·무효·재전달 기록은 별도 사실로 계속 처리한다. PDF 자동 검증 대기와
조치 없는 인수·활성화 상태는 cursor에 기록하되 운영자를 부르지 않는다.
마감된 보고서의 최종 미완료와 병원 근거 자료의 차단은 계속 조치 대상으로 남긴다.

이미지 대체 발행만 성공한 배치는 알리지 않는다. 다른 글의 차단 요약에 성공한 발행을
섞지 않고, 대체 이미지가 추가돼도 같은 차단을 새 알림으로 만들지 않는다.
대체 이미지 편수는 기존 주간 실적에 남긴다. 정상 개인정보 정리 함수도 로그 전용으로
통일했다. 현재 정기 파기 작업은 원래 실패 때만 이 함수를 호출하므로 이 경로만으로
실제 메시지가 줄었다고 계산하지는 않는다.

일일 요약은 병원·이유·건수·담당 역할과 할 일을 먼저 표시한다. 현재 열린 이슈의
대표 그룹 여섯 개와 나머지 수를 구분한다. 과거 실패와 보고서 생성 횟수를 지금 사람이
해야 할 일로 제시하지 않는다. 계약 이행·자동 복구·미확인 상태는 계속 구분한다.

## 잘못된 행동과 수치의 방지

확정 답변을 100번 기준으로 환산했음을 표시한다. 비교 가능 근거가 없으면 전월 증감을
쓰지 않고, 통계 휴리스틱을 ‘의미 있는 상승’으로 단정하지 않는다. 고객에게 전달할
파일이 준비된 상태와 실제 고객 전송 완료를 구분한다.

소개 문의의 버튼도 같은 Admin 출처만 허용하며 다른 호스트는 안전한 내부 화면으로
돌린다. 개인정보 마스킹과 Slack 멘션 escaping을 유지한다. section·header·fields 길이를
사전 검사하고 긴 병원 목록은 블록으로 나눈다. 실패 안내를 없애기 위해 전달 검증을
풀거나, 전송 결과가 불명확한 알림을 재전송하도록 바꾸지 않았다.

## 검증과 적용 범위

검증은 자체 생성한 loopback PostgreSQL 세 개와 Redis에서 수행한다. runner는 운영 dotenv를
읽지 않고 실제 외부 네트워크를 차단한다. Slack은 MockTransport로만 처리하며 실제 채널에
시험 메시지를 보내지 않았다. 병원 원문 생성·측정 구매·발행·보고서 전송은 실행하지 않았다.

신규 회귀 검사는 구버전 보고서 제거와 과거 전달 정정 보존, 최종 실패의 조치 표시,
수신 대상 혼합 거절, 공개 링크 경계, 개인정보·멘션 처리, 긴 목록과 전월 숫자의 방어를 포함한다.
전체 suite는 기존 SQL 동시성·outbox 실패·재시도·복구·PDF 생성 검증까지 함께 실행한다.
예시는 실제 메시지 빌더에서 가상 병원·수치로 생성했으며 Slack에 발송한 화면 캡처가 아니다.

운영 DB·스케줄·전송 엔진·배포 환경은 변경하지 않는다. 기존 중요 장애, 비용/보안 가드,
외부 pipeline watchdog의 발송 조건은 그대로다. 실제 운영 메시지 감소율이나 팀의
처리 시간 개선은 아직 측정하지 않았다. 개별 신규 장애를 하루 메시지 상한으로 버리지 않는다.

스레드 수정이나 이미 전송된 메시지 삭제는 구현하지 않았다. 현재 webhook·채널을 유지하며
알림 생산 단계에서 중복을 제거한다. 기존 outbox에 이미 저장된 payload도 덮어쓰지 않는다.
실제 적용에는 별도 Backend 배포가 필요하며 이번 요청에서는 원격 push·병합·배포하지 않았다.

Slack 형식 검수 참고: 공식 Block Kit section/header 규격과 Incoming Webhooks 문서를
2026-09-17에 확인했다. section 3,000자, header 150자, fields 10개·각 2,000자 제한을 사용한다.
