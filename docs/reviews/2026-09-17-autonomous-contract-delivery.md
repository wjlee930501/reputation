## 수정한 실패 경로

### 1. 당월 누락 슬롯의 일정 복구

`content_calendar.generate_monthly_slots`의 `ensure_quota=True` 경로에서, 유효한 선호 요일이
그 달에 더 남지 않았어도 남은 달력 날짜에 약정 수량을 배정한다. 잘못된 요일·빈 요일·
다음 달을 넘는 시작일은 여전히 거절한다. 기본 strict 초기 일정 정책은 변경하지 않는다.
`monthly_slots`의 당월 복구에는 관측 당일을 하한으로 전달해 새 슬롯을 과거에 배정하지 않는다.
생성된 행 개수가 약정에 미달한 DB IntegrityError를 '이미 만들어진 달력'으로 삼키지 않는다.

### 2. 아침 한 번의 발행 실패가 하루 전체를 잃는 문제

동일한 안전 발행 태스크를 08~23시 매 정각 실행한다. 08시는 첫 공개 시각으로 유지한다.
생성 회수는 기존 01/04/07시 외에 12/18/22시를 추가하며 동일한 claim·일일 예산·재시도
정책을 재사용한다. 21:30 당월 슬롯 복구 뒤의 22시 회수도 포함된다. 유료 호출 예산은 늘리지 않는다.
실제로 재시도 가능한 작업이 더 회수되므로 기존 예산 안에서 실제 사용량은 증가할 수 있다.

### 3. 한 건의 결함이 뒤 병원의 발행을 전부 중단하는 문제

`morning_content_auto_publish`가 글별 오류를 격리해 뒤 항목을 계속 처리한다. 정상 항목을
순회한 뒤 부분 실패를 다시 올려 기존 bounded retry와 실패 관측을 유지한다. Worker 종료·
soft time limit은 삼키지 않는다. 글별 트랜잭션과 발행·캐시 무효화 intent는 그대로다.

### 4. 교체된 일정의 오래된 미발행 작업과 동시 실행

`content_backlog_recovery`가 새 일정으로 교체된 이전 일정의 미이행 슬롯도 회수한다.
이전 공개 이력·사람 편집·유효한 생성 claim은 이동 대상에서 제외하며 만료 claim만 fencing한다.
원래 계약 월을 보존하고, PAUSED나 명시적으로 중지한 일반 일정은 자동 재개하지 않는다.
스캔이 콘텐츠 행을 잠근 채 달력 저장의 병원 lock을 기다리는 경로도 제거했다. 병원 lock이
사용 중이면 그 병원만 보류하고 다음 sweep에서 같은 identity를 회수한다.
실제 PostgreSQL에서 기존 코드의 lock 대기 timeout을 재현했고 수정 후 즉시 보류·이후 회수를 확인했다.

### 5. 목표 선택 중복과 브리프 소유권

`content_target_planner`의 목표/노출 개선 작업 선택을 병원별 짧은 DB 트랜잭션에서 직렬화한다.
선택 후 commit하고 공급자를 호출하므로 lock을 LLM 응답 동안 유지하지 않는다. 달력 lock과
별도 namespace를 써 콘텐츠 행과 달력 저장의 역순 잠금도 피한다. 서로 다른 글이 같은
미사용 질문을 동시에 선택하던 상황을 실제 PostgreSQL 동시 세션으로 검증했다.
다른 병원·다른 글·다른 목표의 ExposureAction이 현재 브리프에 재사용되지 않도록 검사한다.
인간의 메모와 승인된 근거에서 브리프를 구성하는 계약은 보존한다.

### 6. 계약 월 집계와 정상 상태의 구분

`contract_delivery_coverage`가 달력 자체가 없는 경우도 유효한 당월 일정으로 약정을 산출한다.
병원별 미배정·취소로 인한 미충족·기한 지난 미발행·당월 물량의 다음 달 이월을 구분한다.
다른 병원의 초과 배정이나 이전 달의 이월 발행으로 당월 부족을 상계하지 않는다.
하루 운영 요약에 계약 이행 지표를 연결해 실행기 생존만으로 '관측 지표 양호'라고 하지 않는다.
최초 발행, 현재 공개, 달력 배정은 서로 다른 값이다. 취소한 슬롯을 몰래 되살리거나 그만큼
유료 작업을 새로 만들지는 않는다. 현재 지표는 운영 중인 병원의 당월 상태이며, 과거 모든
계약의 재무적 미이행 잔액 전체를 산출하는 원장으로 설명해서는 안 된다.

Admin 현황도 원 계약 월과 해당 월에 유효한 일정의 요금제를 사용한다. 다음 달 요금제와
이월 후 예정일이 당월 분모/분자를 바꾸지 않는다. 유효 일정은 기존 콘텐츠 SELECT에 결합해
현황 endpoint의 11개 SQL 왕복 예산을 그대로 유지했다. 발행 글이 0건인 경우도 검증했다.

## 보존한 안전·운영 경계

HARD 사실/의료 안전 지적, 미확정 검수, 승인 근거 없음, 본문/이미지 공개 검사는 통과 없이
발행하지 않는다. 이미 발행한 글, 사람이 편집하거나 취소한 글을 자동 새 생성으로 덮지 않는다.
생성 실패의 일일 예산과 주제 교체 상한은 그대로이며 무한 재작성은 추가하지 않는다.
원래 공개 표면 캐시 무효화·IndexNow durable intent와 계약 월의 최초 발행 이력도 유지한다.

안전 지적의 실제 사실 여부는 원자료 확인 없이 참/거짓으로 단정하지 않는다. 외부 모델/DB/
broker 장애, 공급자 예산 소진, 계약 시작이 너무 늦은 경우, PAUSED, 명시적 취소나 자료 부재는
여전히 월내 부족을 만들 수 있다. 달력의 행 수가 충분하다고 실제 발행이 보장되지는 않는다.

## 운영 반영 시 필수 순서

이번 요청에서는 코드 수정과 로컬 검증까지만 수행한다. 신규 유료 생성·실제 발행·운영 배포는
실행하지 않았다. 변경된 cadence는 아직 운영에 적용되지 않았다.

`REDBEAT_SCHEDULE_VERSION`은 `2026-09-17.1`이며 `daytime-content-generation-recovery`가 추가됐다.
향후 배포는 Backend 이미지 검증 후 기존 runbook 순서를 따르되 Worker 배포 → RedBeat 영속
스케줄 재조정 → Beat 배포 → 현재 release의 readiness/7개 큐 canary 확인 → API 순서를 지킨다.
마이그레이션은 새로 추가하지 않았지만 이미지의 expected head와 운영 head 일치는 확인해야 한다.
이전의 Site-only 배포 절차를 재사용해서는 안 된다. 단순 이미지 변경만으로 Redis에 남은
예전 08:00 단발 스케줄이 바뀌었다고 가정하지 않는다.

동일한 기존 예산 안에서 낮 시간 자동 회수가 늘어난다. 실제 사용량과 월말의 남은 생성 용량은
배포 후 관측해야 한다. 안전 지적 1건 때문에 수량만 맞추려고 발행 gate를 낮추지 않는다.
